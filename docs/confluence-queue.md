# Scan queue

Scans travel from the plant to the off-site consumer through RabbitMQ. The producer publishes each accepted
scan once, RabbitMQ holds it until the consumer takes it, and a dead-letter queue keeps anything the consumer
can't process. Because RabbitMQ and the producer both run on the plant network, scanning keeps working when the
plant loses its internet connection: scans wait in the queue until the consumer reconnects.

    orthanc-scan-ui ──HTTP──▶ orthanc-scan-producer ──publish──▶ [orthanc.scans exchange]
                                                                    │ routing key scan.created
                                                                    ▼
                                                              (orthanc.scans queue) ──▶ orthanc-scan-consumer
                                                                    │ on failure
                                                                    ▼
                                         [orthanc.scans.dlx exchange] ──▶ (orthanc.scans.dlq queue)

## Topology

| Object               | Name                 | Type     | Settings                                              |
|----------------------|----------------------|----------|-------------------------------------------------------|
| Exchange             | `orthanc.scans`      | Direct   | Durable                                               |
| Queue                | `orthanc.scans`      | Classic  | Durable; bound with routing key `scan.created`; dead-letter arguments below |
| Dead-letter exchange | `orthanc.scans.dlx`  | Direct   | Durable                                               |
| Dead-letter queue    | `orthanc.scans.dlq`  | Classic  | Durable; bound with routing key `orthanc.scans.dlq`   |

The scans queue has these arguments:

| Argument                    | Value               |
|-----------------------------|---------------------|
| `x-dead-letter-exchange`    | `orthanc.scans.dlx` |
| `x-dead-letter-routing-key` | `orthanc.scans.dlq` |

The queues are **classic queues, not quorum queues**. They are durable and messages are persistent, so they
survive a broker restart, but they are not replicated across a cluster.

All names are configurable (`app.scans.*` properties in each app). The values above are the defaults.
Production queues never expire: `app.scans.queue-expires` is left unset, so they have no `x-expires` argument.
Only developer queues set it (see "Developer queues").

### Who declares what

Both the producer and the consumer declare the exchanges, queues and bindings on startup. Whichever starts first
creates them; the other finds them already there.

> **Warning:** the two apps' declarations must match exactly, including the dead-letter arguments. RabbitMQ
> refuses to redeclare an existing queue with different arguments, and the app that starts second fails. To
> change a queue's arguments, delete the queue in the management UI first (after draining it).

## Message format

One message per scan, JSON (`content_type: application/json`), routed with key `scan.created`.

| Field                    | Required | Description                                                          |
|--------------------------|----------|----------------------------------------------------------------------|
| `clientId`               | Yes      | Unique id generated by the UI. Used to de-duplicate scans.          |
| `userName`               | Yes      | Operator who scanned                                                 |
| `currentStage`           | Yes      | Stage where the lot was scanned                                      |
| `lotId`                  | Yes      | Lot scanned                                                          |
| `destinationStage`       | Yes      | Stage the lot is going to                                            |
| `destinationWipLocation` | No       | WIP location within the destination stage                            |
| `scanType`               | No       | Kind of scan                                                         |
| `note`                   | No       | Free-text note                                                       |
| `correctionReason`       | No       | Operator's reason when correcting a location mismatch (max 2000 chars) |
| `locationConfirmed`      | No       | Operator confirmed the lot is here although records show it elsewhere |

## Publishing (producer)

1. The UI posts a scan to the producer.
2. The producer checks it before publishing: lot status (on hold, closed, …), location mismatch, and whether
   the destination is a valid next stage. A rejected scan is returned to the UI and **never queued**.
   - If the consumer can't be reached for the lot check, the producer skips that check and publishes anyway;
     the consumer flags what slips through.
3. An accepted scan is published to `orthanc.scans`.
4. If the UI sends the same `clientId` again, the producer returns the original response without publishing a
   second time. This memory is in-process and is lost when the producer restarts. The consumer de-duplicates
   too (below).
5. If RabbitMQ is unreachable, the request fails and nothing is recorded, so the UI can resend the scan.

Publisher confirms are not enabled.

## Consuming (consumer)

- The consumer listens on `orthanc.scans`, stores each scan and applies it to its lot in one transaction.
- **Delivery is at-least-once.** A scan whose `clientId` is already stored is skipped, so redeliveries and
  repeat publishes are harmless.
- **Retries:** a scan that fails is retried twice more, 1s and then 2s later (3 attempts in total). Each attempt
  is its own transaction, rolled back on failure.
- **Dead-lettering:** if all attempts fail, or the message can't be read as a scan, it is **not requeued**. It
  goes to `orthanc.scans.dlq` with the exception message, stack trace and time. The scans queue keeps moving.

## Failed scans (dead-letter queue)

The consumer has a page for the dead-letter queue at `<consumer-url>/dead-letters`. It lists failed scans
oldest first with lot, user, time and reason. Once the cause is fixed:

- **Retry** sends a scan back to `orthanc.scans`; **Retry all** sends them all. Retrying is always safe,
  because scans already stored are skipped.
- **Discard** removes a scan for good (its body is logged).

The same actions are available as an API:

| Method   | Path                              | Action                 |
|----------|-----------------------------------|------------------------|
| `GET`    | `/api/dead-letters`               | List failed scans      |
| `POST`   | `/api/dead-letters/{id}/retry`    | Retry one              |
| `POST`   | `/api/dead-letters/retry`         | Retry all              |
| `DELETE` | `/api/dead-letters/{id}`          | Discard one            |

The id is the scan's `clientId`, or `sha-…` for a message that can't be read as a scan. Each call works on the
oldest 500 messages.

## Operations

| Environment | RabbitMQ host | Management UI | Consumer dead-letter page |
|-------------|---------------|---------------|---------------------------|
| Test        | `<host>`      | `<url>`       | `<url>/dead-letters`      |
| Production  | `<host>`      | `<url>`       | `<url>/dead-letters`      |

What to watch:

- **`orthanc.scans` depth.** A growing backlog means the consumer is down, can't reach the broker, or is slow.
  During an internet outage this is expected and drains when the link is back.
- **`orthanc.scans.dlq` depth.** Should be zero. Any message here is a scan that hasn't been applied to its lot.

## Developer queues

Developers can run against the test broker with their own queues (see the producer README, "Mode 2"):
`orthanc.scans.<name>` bound to `orthanc.scans` with routing key `scan.created.<name>`, and
`orthanc.scans.dlq.<name>` bound to the shared `orthanc.scans.dlx`.

- Use a **different routing key** as well as a different queue name. The exchange is direct, so a queue bound
  with `scan.created` would receive copies of everyone's scans, and the test consumer would still receive yours.
- Dead-lettered scans are routed by dead-letter queue name, so a developer's dead-letter queue only receives
  their own failed scans.
- Both apps set `app.scans.queue-expires=7d`, which declares the queues with `x-expires`. RabbitMQ deletes each
  queue, and any messages in it, after 7 days with no consumer and no app starting. Starting either app
  recreates the queues.

To remove developer queues sooner, stop both apps and delete the queues in the management UI (**Queues and
Streams** → the queue → **Delete** → **Delete Queue**) or with the HTTP API:

    curl -u <user>:<password> -X DELETE "http://<rabbitmq-host>:15672/api/queues/%2F/orthanc.scans.<name>"
    curl -u <user>:<password> -X DELETE "http://<rabbitmq-host>:15672/api/queues/%2F/orthanc.scans.dlq.<name>"

Queues created before expiry was added must be deleted once, together with the old per-developer exchange
`orthanc.scans.dlx.<name>` (**Exchanges** → the exchange → **Delete this exchange**, or
`DELETE /api/exchanges/%2F/orthanc.scans.dlx.<name>`).
